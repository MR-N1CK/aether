# Aether: AI Developer & Agent Guidelines (AGENTS.md)

This document defines strict operational rules, forensic constraints, and architectural standards for autonomous AI agents, language models, and human developers contributing to or maintaining the Aether codebase.

---

## 1. Forensic Safety & Read-Only Invariant

1. **Static Analysis Only**:
   - **NEVER execute or run any target binaries, scripts, or malware samples** in sample folders (such as `ransomware/`, `kraken3.sh`, test payloads, or victim directories).
   - All threat inspection must be strictly static (source code parsing, AST inspection, regex pattern matching, ELF header inspection, or YARA-X compiled scanning).

2. **No Forensic Contamination**:
   - Never write to or mutate inspected files, permissions, ownership, or timestamps (`mtime`/`ctime`).
   - File opens for inspection must use `safeopen.OpenRegularReadOnly`, `safeopen.OpenReadOnly`, or `safeopen.ReadFileReadOnly` with `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK | O_NOATIME` to prevent symlink traversal attacks, FIFO blocking, and access-time updates where supported by kernel capabilities (`CAP_FOWNER`).

3. **Synthetic Kernel Pseudofs Boundary (`/proc` & `/sys`)**:
   - Kernel pseudofilesystems (`/proc/*`, `/sys/*`) are generated dynamically in-memory by kernel drivers rather than stored on persistent block devices.
   - Because pseudofiles report `stat.Size == 0` and do not support POSIX `O_NOATIME`, live triage modules reading runtime kernel structures (`/proc/modules`, `/proc/net/*`, `/proc/<pid>/*`, `/sys/module/*`) read via bounded buffers (`io.LimitReader` or `os.ReadFile`).
   - All persistent host files (including `/etc`, `/usr`, `/lib`, `/tmp`, `/var`, `/home`, user configs, package manager databases, and custom rules) MUST strictly use `safeopen` primitives.

## 2. Detection Engine Architecture & Rule Lifecycle

When introducing new heuristic patterns or YARA signatures:

1. **Dual-Engine Consistency**:
   - **Native Heuristics** (`internal/scanner/heuristics.go`): Add regexes and parsing checks for instant single-pass script analysis without external dependencies.
   - **Static YARA-X Engine** (`internal/yara/embedded_rules.go`): Add matching YARA-X rules with metadata (`severity`, `score`, `mitre`, `confidence`, `author`).

2. **Mandatory Report & MITRE ATT&CK Enrichment**:
   - Every rule name must be registered in `internal/report/finding.go` inside `PopulateFindingDetails(f *Finding)` with:
     - `Title`: Clear human-readable finding title.
     - `Why`: Plain-English explanation of why the detected pattern is dangerous.
     - `MITRE`: Array of `{Tactic, Technique, TechniqueName}` structs.
     - `Remediation`: Actionable, step-by-step containment instructions.

3. **Severity & Scoring Standards**:
   - `ALERT` (Score 85–100): Confirmed reverse shells, ransomware lockers, exfiltration stealers, rootkit hooks, UID 0 backdoors, or memory injections.
   - `WARNING` (Score 50–84): World-writable configurations in `/etc`, unmapped listening sockets, dropper download pipes, suspicious SUID binaries, or C2 listener servers.
   - `NOTICE` (Score 20–49): Non-executable ELF binaries in `/tmp` owned by invoking user, benign build trees, or unrun modules.
   - `INFO` (Score 0–19): Baseline system observations and acknowledged triage entries.

## 3. Test Suite & Verification Requirements

1. **100% Test Passing Rate**:
   - Run `go test ./...` across all packages before committing any changes.
   - Any added heuristic or YARA rule must have corresponding unit test cases in `internal/scanner/heuristics_test.go` or `internal/yara/engine_test.go`.

2. **Performance & Memory Guardrails**:
   - File hashing and inspection must respect `config.Config.Scan.MaxFileSize` (default 50MB) and `scanner.MemoryBudgetTracker` bounds to prevent out-of-memory crashes on large or sparse files.

## 5. AI Development Interaction & Agent Workflow Protocol

## Core AI Interaction & Workflow Protocol

### 1. Language & Communication
- **Multilingual Comprehension**: Understand instructions and concepts expressed in **Hinglish, Hindi, or English**.
- Respond with clear, professional technical English while honoring vocabulary and intent from Hinglish/Hindi prompts.

### 2. Architecture-First & Investigation
- **Inspect Before Proposing**: Thoroughly examine the existing codebase, file layout, dependencies, and architecture before proposing changes.
- **Clarification Protocol**: Identify the actual objective and proactively ask clarifying questions whenever key technical details, requirements, or constraints are missing.

### 3. Professional Technical Specification
- **Prompt Transformation**: Convert informal descriptions or brief requests into a structured, comprehensive technical specification before planning.
- Every comprehensive plan must cover:
  1. Functional Requirements
  2. Technical Constraints
  3. Architecture & Data Flow
  4. Security & Privilege Boundaries
  5. Performance & Resource Bounds
  6. Edge Cases & Error Handling
  7. Verification Strategy & Test Cases
  8. Acceptance Criteria

### 4. Strict Approval Gate & Scope Control
- **No Unsolicited Modifications**: My initial idea or request is **NOT permission to modify code or execute modifying commands**.
- **Approval Protocol**: Present the complete proposed prompt and implementation plan first, then **wait for explicit user approval** before touching any implementation files or running mutating commands.
- **Revision Protocol**: If changes are requested on the plan, revise the proposed specification and request approval again.
- **Strict Scope**: Implement strictly the agreed scope. Approval of a plan is not permission to implement future or out-of-scope tasks.

### 5. Code Quality & Truthful Verification
- **No Unnecessary Rewrites**: Preserve existing working architecture, comments, style, and structure. Do not perform gratuitous refactors.
- **No Unsupported Assumptions**: Verify against real files rather than hallucinating paths, imports, or APIs.
- **Truthful Testing**: Run relevant automated test suites and report genuine, unvarnished test results, modified files, limitations, and unverified behavior. **Never fabricate test results**.

### 6. Safe & Authorized Cybersecurity Practice
- **Containment**: All testing must follow safe, authorized, and strictly contained cybersecurity practices.
- **Zero Insecure Defaults**: Never introduce hardcoded credentials, world-writable permissions, unauthenticated backdoors, or unmonitored external network connections.
- **No Secret Exposure**: Never log, expose, or commit secrets, tokens, API keys, or private key material.
