# Aether: AI Developer & Agent Guidelines (AGENTS.md)

This document defines strict operational rules, forensic constraints, and architectural standards for autonomous AI agents, language models, and human developers contributing to or maintaining the Aether codebase.

---

## 1. Forensic Safety & Read-Only Invariant

1. **Static Analysis Only**:
   - **NEVER execute or run any target binaries, scripts, or malware samples** in sample folders (such as `ransomware/`, `kraken3.sh`, test payloads, or victim directories).
   - All threat inspection must be strictly static (source code parsing, AST inspection, regex pattern matching, ELF header inspection, or YARA-X compiled scanning).

2. **No Forensic Contamination**:
   - Never write to or mutate inspected files, permissions, ownership, or timestamps (`mtime`/`ctime`).
   - File opens for inspection must use `safeopen.OpenRegularReadOnly` with `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK | O_NOATIME` to prevent symlink traversal attacks, FIFO blocking, and access-time updates where supported by kernel capabilities (`CAP_FOWNER`).

---

## 2. Detection Engine Architecture & Rule Lifecycle

When introducing new heuristic patterns or YARA signatures:

1. **Dual-Engine Consistency**:
   - **Native Heuristics** (`internal/scanner/heuristics.go`): Add regexes and parsing checks for instant single-pass script analysis without external dependencies.
   - **Static YARA-X Engine** (`internal/yara/embedded_rules.go`): Add matching YARA-X rules with metadata (`severity`, `score`, `mitre`, `confidence`, `author`).

2. **Mandatory Report & MITRE ATT&CK Enrichment**:
   - Every rule name must be registered in `internal/report/finding.go` inside `PopulateFindingDetails(f *Finding)` with:
     - `Title`: Clear human-readable finding title.
     - `Why`: Plain-English explanation of why the detected pattern is dangerous.
     - `MITRE`: Array of `{Tactic, Technique, TechniqueName}` structs.
     - `Remediation`: Actionable, step-by-step containment instructions.

3. **Severity & Scoring Standards**:
   - `ALERT` (Score 85–100): Confirmed reverse shells, ransomware lockers, exfiltration stealers, rootkit hooks, UID 0 backdoors, or memory injections.
   - `WARNING` (Score 50–84): World-writable configurations in `/etc`, unmapped listening sockets, dropper download pipes, suspicious SUID binaries, or C2 listener servers.
   - `NOTICE` (Score 20–49): Non-executable ELF binaries in `/tmp` owned by invoking user, benign build trees, or unrun modules.
   - `INFO` (Score 0–19): Baseline system observations and acknowledged triage entries.

---

## 3. Test Suite & Verification Requirements

1. **100% Test Passing Rate**:
   - Run `go test ./...` across all packages before committing any changes.
   - Any added heuristic or YARA rule must have corresponding unit test cases in `internal/scanner/heuristics_test.go` or `internal/yara/engine_test.go`.

2. **Performance & Memory Guardrails**:
   - File hashing and inspection must respect `config.Config.Scan.MaxFileSize` (default 50MB) and `scanner.MemoryBudgetTracker` bounds to prevent out-of-memory crashes on large or sparse files.

---

## 4. UI & Output Contract

1. **Executive Studio Pro Palette**:
   - Follow color and styling tokens in `internal/ui/theme/theme.go`.
   - Maintain clear categorization into:
     - 🚨 **MALICIOUS THREATS (Alerts)**
     - ⚠️ **SUSPICIOUS ANOMALIES (Warnings)**
     - 🛡️ **SAFE ASSETS (Inspected Clean Objects)**

2. **Offline HTML Integrity**:
   - HTML reports generated by `internal/report/html/template.go` must remain 100% self-contained with inline CSS/JS/SVG, zero external network requests, strict CSP nonces (`crypto/rand`), and DOM-safe dynamic element construction (no `innerHTML`).
